# OEP でできること（使い方ごとのガイド）

開発ボードに OEP の firmware を入れると、PC のソフトウェアから使う「プローブ」になります。プローブは PC と相手のチップ・基板の
間に入り、デバッグ、通信、信号の出し入れ、波形の取り込みを、どれも同じ方法で受け持ちます。

この文書は、やりたいことから始めて、何を用意し、どう配線し、何を設定すれば、何が解決できるかをまとめたものです。
設定項目の全体は [設定項目](settings.ja.md)、デバッグの相手ごとの詳細は [デバッグの対応ターゲット](debug-targets.ja.md)、
波形の取り方の違いは [キャプチャの使い分け](capture.ja.md) にあります。

## やりたいことから選ぶ

| やりたいこと | 解決できること | 節 |
|---|---|---|
| CH32（WCH の RISC-V マイコン）に書き込む・デバッグする | WCH-Link が無くても、Arduino IDE や CLI から書き込み、止めて中を見られる | [1](#1-ch32-に書き込むデバッグする) |
| 相手のマイコンのログを見る | UART が空いていても空いていなくても、普通のシリアルモニタやツールでログを読める | [2](#2-相手のログを見るコマンドを送る) |
| ARM Cortex-M の中を見る | SWD でメモリとレジスタを読み書きし、止めて動かせる | [3](#3-arm-cortex-m-の中を見る) |
| 波形を取る（ロジックアナライザとして） | 信号の時間関係を取り込み、ファイルに残し、プロトコルを解読できる | [4](#4-波形を取る) |
| センサや IC と I2C / SPI で話す | プローブが通信を始める側になり、相手のレジスタを読み書きできる | [5](#5-センサや-ic-と-i2c--spi-で話す) |
| 自分のマイコンの I2C / SPI のドライバを試す | プローブが相手のセンサの代わりになり、来た要求と返す値を自分で決められる | [6](#6-自分のマイコンの-i2c--spi-のドライバを試す) |
| 信号を出す・測る | GPIO、PWM、パルスの数、アナログの値を、PC から出し入れできる | [7](#7-信号を出す測る) |
| 自動テストの治具にする | 書き込み、ログ、波形、信号の出し入れを、テストのコードから繰り返し行い、合否を出せる | [8](#8-自動テストの治具にする) |
| 離れた場所から使う | Wi-Fi で、USB をつながずにプローブを使える | [9](#9-離れた場所から使う) |
| 1 台を治具として据え置く | 起動のたびに同じ配線・同じ待機状態で使える。ほかの PC からも同じ名前で指せる | [10](#10-プローブを治具として据え置く) |

## 0. 共通の準備

### 用意するもの

- **プローブにするボード**: RP2040 / RP2350（Pico、Pico 2 など）、ESP32-P4 / P4X、classic ESP32（DevKitC など）。どの機能が
  どのボードにあるかは [ボード](boards.ja.md#チップごとにできること) の表で確かめます。迷ったら次を目安にします。
  - デバッグと通信を手軽に: RP2040 / RP2350。
  - 速い波形の取り込み、多チャネル、据え置きの治具: ESP32-P4 / P4X。
  - Wi-Fi で使う、DAC を使う: classic ESP32。
- **データ通信のできる USB ケーブル**。
- **PC のソフトウェア**: 下の「道具」から、やりたいことに合うものを入れます。
- **配線の線**: ジャンパ線など。プローブと相手の **GND は必ずつなぎます**。

### 電気の注意

- プローブのピンはどれも 3.3 V 系です。5 V の相手には、レベル変換をはさみます。プローブはレベルを変換しません。
- プローブから相手に電源を出すときは、ボードの 3.3 V / 5 V の端子の許す電流の範囲で使います。相手に別の電源があるときは、
  電源どうしをつながず、GND だけを共通にします。
- 相手の電源が入っていない間に、プローブのピンから相手に電圧をかけ続けないようにします（相手のピンから電源に回り込みます）。

### firmware を入れる

[使い始める](getting-started.ja.md#1-firmware-を焼く) のとおり、ボードに合う firmware を書き込みます。firmware には配線を
焼き込んでいないので、同じ firmware でどんな配線にも使えます。

### 道具

| 道具 | 何に使うか | 入手 |
|---|---|---|
| `oep` コマンドと Python の `oep_client` | プローブの確認（`oep dump`）、設定（`oep settings`）、配線の調査（`oep pins`）。Python から全部の機能を使う | [oep-client-python](https://github.com/Open-Embedded-Probe/oep-client-python)（`pip install oep-client-python`） |
| `ch32rv` | CH32 の書き込み、デバッグ（GDB server）、ログの表示、復旧 | [ch32rv](https://github.com/ch32-riscv-ug/ch32rv) |
| Arduino IDE と ArduinoCore-CH32RV | CH32 のスケッチを、プローブ経由で書き込む | [ArduinoCore-CH32RV](https://github.com/ch32-riscv-ug/ArduinoCore-CH32RV) |
| WireSkein | 波形の取り込み、解読、表示、テストでの照合 | [wireskein](https://github.com/Open-Embedded-Probe/wireskein) |
| pytest のプラグイン | テストごとに波形を残して照合する | [pytest-embedded-wireskein](https://github.com/Open-Embedded-Probe/pytest-embedded-wireskein) |

### 口（ポート）の名前を付ける

相手のチップにつないだピンの組に名前を付けておくと、どの道具からも `oep://<プローブ>/<口>` で同じ相手を指せます。
名前はプローブに保存するので、PC を替えても、道具を替えても同じです。

- 名前は、プローブのピンのラベル（設定の `channel.{}.label`）で付けます。形は `口.線@相手のピン` です。
  例: `mcu.swdio@pa13`、`mcu.swclk@pa14`、`mcu.rx@pa9`、`mcu.nrst`。線の名前の慣行は `swdio`、`swclk`、`swio`、`rx`、`tx`、`nrst` です。
  役目の無い線は `mcu@pb6` と書けます。
- `<プローブ>` はプローブの個体の ID（unit id）で、`oep dump` で分かります。
- ラベルを付けなくても、どの機能もピンの番号を直接指定して使えます。名前は、繰り返し使う相手のための便利な記録です。
- デバッグの線は `oep pins` でスキャンして見つけ、`--save` でそのままラベルにできます（[1](#1-ch32-に書き込むデバッグする)）。

詳しい規則は [設定項目](settings.ja.md#ピンのラベル口と線の名前) にあります。

## 1. CH32 に書き込む・デバッグする

**解決できること**: WCH-Link を買わなくても、手元の Pico や ESP32 で CH32 に書き込み、止めてメモリやレジスタを見られます。
1 台のプローブに複数の相手をつなぎ、口の名前で選べます。

**用意するもの**: プローブ、相手の CH32（評価ボードや自作の基板）、`ch32rv` または Arduino IDE と ArduinoCore-CH32RV。

**配線**:

| 相手 | 線 | 相手のピン |
|---|---|---|
| CH32V002 / V003 / V004 | 1 線（SWIO） | PD1 |
| CH32V005 / V006 / V007、CH32M007 | 1 線（SWIO） | PD1 |
| CH32X033 / X035 | 2 線（RVSWD） | PC18（SWDIO）、PC19（SWCLK） |
| CH32V103、V203 / V208、V30x、L103 / M103、V205、V407 / V467、X305 / X315 | 2 線（RVSWD） | PA13（SWDIO）、PA14（SWCLK） |
| CH32M030 | 2 線（RVSWD） | PA3（SWDIO）、PA2（SWCLK） |

- プローブの側は、どのピンでも使えます（ボードの表で出しているピン）。GND をつなぎます。
- 相手の NRST をプローブのピンにつなぐと、リセットをかけながらの接続や、デバッグの線が使えなくなったときの復旧ができます。
  CH32V003 などは、NRST の端子が option bytes で無効になっていることがあります（[デバッグの対応ターゲット](debug-targets.ja.md)）。
- 相手ごとの詳しい注意（線の休ませ方、速さの上限など）は [デバッグの対応ターゲット](debug-targets.ja.md) にあります。

**設定**:

1. 線を見つけてラベルにする（推奨）。配線したピンが分かっていれば、`oep settings set` でラベルを書くだけでもかまいません。

   ```sh
   oep pins oep://<プローブ> --wire rvswd --name mcu --save    # 1 線の相手は --wire swio
   ```

   `oep pins` は、空いているピンの組で相手に話しかけ、答えたピンを `mcu.swdio` / `mcu.swclk`（1 線なら `mcu.swio`）として保存します。
   リセットの線が見つかれば `mcu.nrst` も付けます。スキャンは相手に信号を出すので、つないでいる相手の分かるときに使います。
2. 線の休ませ方や速さは、ふつうは設定しません。プローブと `ch32rv` が相手に合わせて選びます。決まった相手で固定したいときだけ、
   [設定項目](settings.ja.md#デバッグの線) の `channel.{}.rest` を使います。

**使い方**:

- Arduino IDE: ボードに ArduinoCore-CH32RV の CH32 を選び、ポートに `oep://<プローブ>/<口>`（またはプローブのシリアルポート）を選んで
  「書き込み」。
- コマンドライン:

  ```sh
  ch32rv --probe oep://<プローブ>/mcu target info     # 相手を確かめる
  ch32rv --probe oep://<プローブ>/mcu flash app.elf   # 書き込み、照合、リセット、起動
  ch32rv --probe oep://<プローブ>/mcu gdb             # GDB server（127.0.0.1:3333）
  ```

- Python からは `oep_client.riscv` の `Wire` と `RiscvDm` で、attach、halt、メモリの読み書き、レジスタを扱えます
  （[使い始める](getting-started.ja.md#rvswd-で-ch32-をデバッグする)）。

**注意**:

- アプリがデバッグの端子を GPIO にしたり、深いスリープに入ったりすると、つながりません。NRST をつないでいれば、
  `ch32rv recover --method nrst` で戻せます。
- デバッグの接続を閉じても、相手は止まったままのことがあります（止めたまま閉じたとき）。動かしたいときは、閉じる前に resume します。

## 2. 相手のログを見る・コマンドを送る

**解決できること**: 相手のマイコンが出すログを、PC で読めます。UART で出すログも、UART を使わずにデバッグの線で出すログも読めます。
設定すれば、プローブのシリアルポートを普通のシリアルモニタで開くだけで、ログが流れてきます。

方法は 3 つあります。

| 方法 | 相手の出し方 | 配線 | 向き |
|---|---|---|---|
| A. UART で受ける | 相手の UART（`Serial.print` など） | 相手の TX → プローブの RX、（送るなら）プローブの TX → 相手の RX、GND | 両方向 |
| B. デバッグの線で受ける | debug module の郵便受け（CH32 の `sdi`、`dmdata`、`dmseq`） | [1](#1-ch32-に書き込むデバッグする) と同じデバッグの線、GND | `sdi` は相手 → PC、`dmdata` / `dmseq` は両方向 |
| C. シリアルポートへ素通し | A か B を、セッションの無い間だけプローブのシリアルポートへ流す | A か B と同じ | 相手 → PC |

**A. UART で受ける**

- 相手の TX を、プローブの UART の RX にできるピンへつなぎます（ESP32 はどのピンでも、RP2 は決まった組だけ。[ボード](boards.ja.md)）。
- 速さ（baud）と形式（8N1 など）は、受け始めるときに道具で指定します。プローブの本体設定ではありません。
- Python の `FixtureUartIO`、`ch32rv monitor --source uart` で読めます。読んだログはプローブの中に溜まり、あとから続きを読めます。

**B. デバッグの線で受ける**

- UART の端子を空けられない相手や、UART を他に使っている相手向けです。相手のスケッチが、コアの用意した出力先（ArduinoCore-CH32RV の
  [デバッグ出力](https://github.com/ch32-riscv-ug/ArduinoCore-CH32RV/blob/main/docs/debug-output.ja.md)）を使って出します。
- `ch32rv monitor --source dmseq`（または `sdi`、`dmdata`）で読み、入力も送れます。書き込みとログの表示が、同じ口で行えます。

**C. シリアルポートへ素通しする**

- プローブのシリアルポートを Arduino IDE のシリアルモニタや端末ソフトで開くだけで、ログを見たいときに使います。
- 設定（保存しておけば起動のたびに効きます）:
  - UART を流す: `oep.fixture.uart` の `passthrough.<口>.rx`、`.baud`、`.format`。
  - デバッグの線のログを流す: `oep.target.console` の `passthrough.<口>.wire`、`.swdio`、`.swclk`、`.mechanism`。
  - `<口>` はプローブのシリアルポートの名前（`cdc0` など）です（[設定項目](settings.ja.md#素通し)）。
- 素通しは、ほかの道具がプローブを使っている間は止まり、終わると戻ります。書き込みの道具は、同じポートでそのまま使えます。
- 素通しは相手 → PC の向きだけです。相手へ送るには A か B を使います。

## 3. ARM Cortex-M の中を見る

**解決できること**: SWD で ARM Cortex-M につなぎ、メモリと周辺のレジスタを読み書きし、コアを止めて動かせます。
Python から、相手の RAM に置いた関数を呼ぶこともできます。

**用意するもの**: SWD を持つプローブ（[ボード](boards.ja.md#チップごとにできること)）、相手の Cortex-M、Python の `oep_client`。

**配線**: 相手の SWDIO と SWCLK（STM32 なら多くは PA13 / PA14）、GND。必要なら NRST。

**使い方**: `oep_client.arm` の `SwdWire`（attach。マルチドロップの相手は TARGETSEL を指定）、`ArmAdi`（DP / AP）、`MemAp`
（メモリ）、`CortexM`（halt、resume、レジスタ、関数の呼び出し、システムリセット）を使います。

**注意**: Cortex-M の flash に書き込む道具（flash loader）は用意していません。書き込みは Python から自分で行います。
GDB server もありません。

## 4. 波形を取る

**解決できること**: ロジックアナライザとして、信号の変化を時間つきで取り込み、ファイルに残し、UART、SPI、I2C、CAN、LIN、
CH32 のデバッグの線などを解読できます。アナログの値も一緒に取れます（対応するボード）。

**用意するもの**: キャプチャに対応するボード（速さとチャネル数は [ボード](boards.ja.md#チップごとにできること)。速い信号には ESP32-P4 / P4X）、
WireSkein。

**配線**: 見たい信号をプローブのピンにつなぎ、GND をつなぎます。キャプチャは聞くだけなので、ほかの機能が使っているピンも取れます。

**使い方**:

```sh
wireskein capture --source oep:oep://<プローブ> --channels SDA=GPIO47,SCL=GPIO48 --rate 20M --samples 200k -o i2c.wireskein
wireskein gui i2c.wireskein          # ブラウザで表示
wireskein convert i2c.wireskein i2c.sr   # PulseView で開くとき
```

取り方は、キャプチャだけで使うか、デバッグや治具のラベルと組み合わせて使うかで変わります。違いは
[キャプチャの使い分け](capture.ja.md) にまとめてあります。

## 5. センサや IC と I2C / SPI で話す

**解決できること**: マイコンのプログラムを書かずに、PC から I2C / SPI の相手（センサ、EEPROM、表示器など）と通信し、
レジスタを読み書きして、相手の振る舞いを確かめられます。

**用意するもの**: I2C / SPI の controller を持つプローブ、相手の部品、Python の `oep_client`。

**配線**:

- I2C: SDA、SCL、GND。プルアップ抵抗（数 kΩ）が要ります。相手の基板に無ければ付けます。
- SPI: SCK、MOSI、MISO、CS、GND。

**使い方**: `oep.fixture.i2c-controller` / `oep.fixture.spi-controller` を Python から使います。アドレス、速さ、SPI の mode は、
通信のたびに指定する条件で、本体設定ではありません。プローブの I2C / SPI は GPIO で作っているので、速さの上限は
[ボード](boards.ja.md#チップごとにできること) の表のとおりです。

## 6. 自分のマイコンの I2C / SPI のドライバを試す

**解決できること**: 開発中のマイコン（controller）の相手を、プローブが演じます。本物のセンサが無くても、返す値を決めて
ドライバを試せます。相手から来た書き込みと読み出しの要求は、プローブに溜まり、あとで読めます。

**用意するもの**: I2C / SPI の target を持つプローブ（[ボード](boards.ja.md#チップごとにできること)）、開発中のマイコン、Python の `oep_client`。

**配線**: [5](#5-センサや-ic-と-i2c--spi-で話す) と同じ線を、開発中のマイコンとプローブの間につなぎます。I2C のプルアップは、
どちらかの側に付けます。

**使い方**: `oep.fixture.i2c-target` / `oep.fixture.spi-target` を Python から使います。I2C は自分のアドレスを、SPI は mode を決め、
返すデータを先に積んでおき、待ち受けます。

## 7. 信号を出す・測る

**解決できること**: スイッチを押す代わりにピンを動かす、相手の出力を読む、PWM で LED やモーターのドライバを試す、
周波数を測る、アナログの電圧を出す・取り込む、といったことを PC から行えます。

| 機能 | 使う interface | できること |
|---|---|---|
| GPIO | `oep.fixture.gpio` | 入力（pull の有無）、出力 high / low、open drain（リセットの線などに） |
| PWM | `oep.fixture.pwm` | 周波数と duty の出力 |
| パルスを数える | `oep.fixture.counter` | 決めた時間のエッジの数、そこから周波数 |
| アナログを出す | `oep.fixture.dac` | DAC のあるボードだけ（classic ESP32 など） |
| アナログを取り込む | `oep.fixture.analog` | 決めた速さで電圧の値を取り込む |

**配線**: 使うピンと GND。出力を相手の出力とぶつけないようにします。

**使い方**: Python の `oep_client.fixture` を使います（[使い始める](getting-started.ja.md#gpio-と-uart試験の治具)）。
ある機能が使っているピンは、ほかの機能からは使えないので、テストのコードが 2 つの出力をぶつけることはありません。
使い終わったピンは空きの状態に戻ります。空きの状態を決めたいときは [設定項目](settings.ja.md#ピンの空きの状態と使用禁止) の
`channel.{}.idle` を使います。

## 8. 自動テストの治具にする

**解決できること**: 書き込み、リセット、ログの確認、信号の出し入れ、波形の取り込みと照合を、テストのコードで繰り返せます。
結果は合否と測った値で残り、CI に載せられます。

**用意するもの**: 治具にするプローブ（チャネルの多い ESP32-P4 / P4X が向きます）、相手の基板、pytest、
`oep_client`、WireSkein と pytest-embedded-wireskein。CH32 なら ch32rv と ArduinoCore-CH32RV の試験の道具。

**配線**: デバッグの線、標準の UART、NRST、BOOT 系の端子（相手にあれば）を必ずつなぎ、ほかのピンもできるだけ多くつなぎます。
後から試したくなる機能の線が、すでにつながっているようにするためです。

**設定**: [10](#10-プローブを治具として据え置く) の据え置きの設定をします。配線はラベルに書いておくと、テストのコードは
ピンの番号ではなく `mcu.rx` のような名前で線を探せます。

**使い方**: テストの中で、プローブのセッションを取り、必要な機能を使い、終わったら手放します。セッションが終われば、
そのテストが割り当てたピンや接続はすべて解放されるので、次のテストに持ち越しません。波形は WireSkein の記録と照合で
テストの結果にします（[WireSkein のキャプチャの試験](https://github.com/Open-Embedded-Probe/wireskein/blob/main/docs/capture-test-guide.ja.md)）。

## 9. 離れた場所から使う

**解決できること**: USB をつながずに、同じネットワークの PC からプローブを使えます。

**用意するもの**: Wi-Fi を持つプローブ（classic ESP32）。

**設定**: シリアルポートから `wifi.<番号>.ssid` と `wifi.<番号>.passphrase` を設定して保存します（[使い始める](getting-started.ja.md#6-wi-fi-でclassic-esp32)）。
固定アドレスにするときは `ipv4.<番号>.*` を使います。

**使い方**: `oep find` で見つけ、`oep://<プローブ>?via=net` で開きます。どの道具も同じアドレスで使えます。

**注意**: OEP には認証がありません。信頼できるネットワークか、認証したトンネルの中だけで使います。

## 10. プローブを治具として据え置く

**解決できること**: 起動のたびに同じ状態で使える治具になります。配線の名前、使わないピンの待機状態、触らせないピン、
ログの素通しが、どの PC から使っても同じです。

**設定する順番**:

1. **触らせないピンを決める**: ボードの部品（LED、ボタン、起動のストラップ）につながったピンを `channel.{}.disable` にします。
2. **配線に名前を付ける**: 相手ごとに口の名前でラベルを付けます（`oep pins --save` か `oep settings set`）。
3. **待機状態を決める**: 相手の入力を浮かせたくない線（BOOT0、リセット、チップセレクトなど）に `channel.{}.idle` を付けます。
4. **ログの素通しを決める**（使うなら）: [2](#2-相手のログを見るコマンドを送る) の C。
5. **保存して控えを取る**: `oep settings save` で起動のたびに効くようにし、`oep settings export` でファイルに控えます。
   firmware を更新した後や、別の個体に移すときは `oep settings import` で戻します。

相手の型番やメモは、プローブのメモ欄（`oep.probe.memo/port/<口>`）に置くと、どの PC からも同じ記録を読めます。

各項目の意味と効くタイミングは [設定項目](settings.ja.md) にあります。

## できないこと

- OEP のデバッグの線は RVSWD、SWIO（WCH の RISC-V）と SWD（ARM）です。JTAG、ESP32 や AVR の書き込み、ほかの独自の線は扱いません。
- 相手ごとの書き込みの手順は、PC の道具（ch32rv など）が持ちます。デバッグの線につながるからといって、どの相手にも書き込めるわけではありません。
- プローブはレベル変換も電源の切り替えもしません。必要なら外付けの回路を使います。
